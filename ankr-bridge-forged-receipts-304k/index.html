Ankr Bridge Forged Receipts: How Valid Signatures Drained $304,500

Written by Crypto Desk · Last verified: 2026-11-12 00:00 UTC

On November 9, 2026, an attacker pulled $304,500 from Ankr Bridge using five forged withdrawal receipts [SlowMist + Blockaid, dual-source verified]. The signatures on those receipts were cryptographically valid — the bridge simply never checked whether the deposit event each receipt pointed to had already been spent. That distinction — valid signature, unspent-check missing — is the whole story, and it is the part worth reading twice.

Mechanism Deep Dive: What a "Forged Receipt" Actually Is

Bridges that use an optimistic or receipt-based model work like this: you deposit on chain A, a receipt is produced, and the bridge mints or releases funds on chain B against that receipt. The security assumption is: one deposit event → one spent receipt.

The Ankr incident broke exactly that assumption:

  1. One real deposit, five receipts. The attacker produced five forged withdrawal receipts, and all five pointed at the same legitimate Optimism deposit [SlowMist + Blockaid].
  2. The signatures checked out. Each receipt carried valid signature data, so a naive verification path — "does this signature match the depositor?" — passes.
  3. The missing check was the spend state. The bridge did not verify that the underlying deposit event had not already been redeemed. In database terms, the receipt table was keyed to a deposit that was already marked spent — but the bridge's check path never looked at that column.
  4. Result: $304,500 released against five claims on one deposit [SlowMist].

Why this page survives the news cycle: this is not "private keys were stolen." This is a logic bug in receipt lifecycle handling — the same bug class shows up in claim systems, airdrop portals, and any flow where "proof of X" can be presented more than once. Understanding it makes you better at evaluating every bridge and claim you ever touch.

Self-Check: Did I Bridge Through Ankr?

  1. Pull your Ankr Bridge history (in-app or on-chain): list every deposit and every completed withdrawal.
  2. Match deposits to withdrawals 1:1. If one deposit produced more than one completed withdrawal, that is the fingerprint of this exploit — collect the tx hashes.
  3. Check pending receipts. Any withdrawal still in-flight after 11-09 is worth flagging; the team has been processing claims.
  4. Keep screenshots and tx hashes. Claim processes run on evidence; an on-chain hash is the strongest form.
  5. Don't bridge again through the same path until you have read the team's post-incident update on the spend-state check.

FAQ

How much was stolen? $304,500 [SlowMist, confirmed by Blockaid].

Were the attacker's signatures fake? No — the signatures were valid. The bridge's missing check was on the deposit's spent state, not on signature authenticity [SlowMist].

Why five receipts? Because five claims on one deposit yielded five releases. The count of five is a forensic detail that ties directly to the single-deposit mechanism [SlowMist].

Is Ankr Bridge safe now? The specific receipt lifecycle bug is identified; whether the spend-state check is enforced everywhere the model is used is what the post-incident update will answer. Until you have read it, treat new bridges as "check the team's response first."

How is this different from the Binance heist? Different bug class: Binance was a coordinated multi-chain sweep of ~$6.3B [TRM Labs + Chainalysis]; Ankr was a single-logic exploit of $304,500. Size is not the lesson — the missing invariant is.
